# Security

ZIP lookup routes are public and read-only; they do not require accounts or API keys. Owner tokens are optional credentials for associating caller activity with an anonymous owner and managing that owner's linked tokens. Primary tokens have global owner scope; linked tokens have `read` or `read-write` scope, with read-only MCP tool filtering and insufficient-scope bearer challenges on protected routes. There are no user accounts, profiles, or passwords. ZIP input and radius/coordinate values are validated, SQL uses bound parameters, and CORS defaults to `*` without credentialed requests. Forwarded client-IP headers are honored only from trusted peers.

Request limits default to 120 read requests/minute, 10 non-read requests/minute, 120 health requests/minute, and a 240 request/minute ceiling across endpoint classes. Valid Bearer tokens use token-specific buckets; requests without a valid token use the resolved client IP. Counters use SQLite by default and may use a configured Valkey/Redis backend; if that backend is unavailable, the server falls back to in-process counters and reports degraded cache health. Client IPs are normalized before use, and counter keys do not expose raw IP addresses. Expired events are removed as requests arrive.

The default SQLite database uses separate read-only and single-writer pools with WAL, a 10 second busy timeout, and a shutdown WAL checkpoint. Keep it on local storage; network and FUSE filesystems are unsupported. Remote libSQL/Turso is supported with TLS URLs and provider-managed access controls. Remote tables and indexes use the `srv_` prefix, and the remote database itself is not included in local backup archives. An optional `server.database.cache` stores a read replica in a separate SQLite file under the data directory, with owner-only directory and file permissions; cached reads bypass the file while it is dirty or older than `max_age`. Keep connection URLs containing credentials and `server.database.token` in `secrets.yml`; credentials are never written to logs or health responses.

`/server/healthz`, `/server/privacy`, `/server/terms`, `/server/about`, `/server/help`, preferences, and the API documentation pages are public. The root `/healthz` alias is disabled by default and, when enabled, uses the same health handler and content negotiation. Browser preference and token-management mutations use same-origin POST forms with CSRF tokens. Preference cookies are written only after the visitor accepts the Preferences consent category. Declining consent or withdrawing Preferences expires existing theme, language, and application preference cookies and returns `Clear-Site-Data: "cache", "storage"`; the consent choice itself remains stored. Consent changes are recorded as `compliance.consent_updated` with an anonymized client IP and the configured privacy-policy version. API token-management routes require the `Authorization: Bearer` header with the owner's primary token, except primary-token issuance, which is public and issues a new anonymous owner. API routes do not accept owner cookies. Linked tokens cannot manage tokens. `/api/{api_version}/me` uses the caller IP from the TCP peer or a configured trusted proxy. GeoIP skips private/reserved addresses and fails open when lookup data is unavailable. Country and ASN data use PDDL iptoasn.com files; city data uses DB-IP under CC BY 4.0. Downloads are verified against their release checksums before replacing live databases; a mismatch retries the checksum and asset once. If they still disagree, a sane live database is kept. With no live copy, a candidate is installed only when it opens as a valid MMDB with sane metadata, and its health remains degraded until a verified update. Failed or unverified updates do not advance `{data_dir}/security/geoip/.last_updated`; the private `.update_failed` marker keeps GeoIP health degraded until a verified update clears it. The scheduler refreshes enabled GeoIP weekly, and ZIP lookup remains available when GeoIP data is missing or stale.

Configured IP and domain blocklists are loaded from `{data_dir}/security/blocklists/`; the built-in FireHOL IPv4 feed and each enabled HTTPS source keep separate last-success timestamps. Entries overlapping private, loopback, link-local, CGNAT, or trusted proxy ranges are skipped. The blocklist check runs after rate limiting and before GeoIP; IP allowlist entries bypass those three checks while authentication, CSRF, and path security remain enforced. Failed refreshes keep the prior snapshot. Sources older than 72 hours report degraded health, and sources that have never loaded report an error.

The daily `cve_update` task keeps the unfiltered NVD CVE array in `{data_dir}/security/cve/nvd.json`, merging incremental updates by CVE ID. An optional Trivy OCI database is controlled by `data.trivy.enabled`; pulls are skipped until its `NextUpdate` time. NVD rate limits defer work to a later scheduler run. Dataset health is non-critical: missing databases report error, and data older than 72 hours reports degraded. The optional NVD API key belongs in `secrets.yml`.

The `/server/dpo` page and its JSON mirror expose `server.contact.dpo.email`, falling back to `server.contact.general.email`. They never expose the private `server.contact.admin.email`; when neither public address is configured, the page links to `/server/security` instead.

Owner and linked tokens use the `own_` prefix. The database stores a SHA-256 lookup hash and an AES-256-GCM encrypted copy so owners can reveal their tokens from the token page. Revealed values are not included in token-list responses. A token's raw value is returned by issue, reveal, or rotate actions; protect it like a password. Rotating a primary token preserves the owner and linked tokens. Revoking the primary deletes that owner and all associated tokens and resources. See [API reference](api.md) for the routes.

The operator token uses the `adm_` prefix and is stored in `secrets.yml`, separate from `server.yml`. It is generated on first startup and printed to the process console once. The file is created with `0600` permissions. The token-encryption key is stored in the same file; losing it prevents decryption of stored token values.

The server stores its installation HMAC secret, cookie-signing key, and CSRF key in the database. Cookie-signing keys rotate every 90 days; CSRF keys rotate every 180 days and when the operator token is regenerated. Previous HMAC keys remain valid for seven days. Use `zipcodes --maintenance secret rotate installation_secret` to rotate the installation secret, or `zipcodes --maintenance secret rotate encryption_key` to rotate the `secrets.yml` AES key and re-encrypt stored values. Both manual rotations require root or an interactive operator-token confirmation and a typed phrase. Secret rotation has no web or API interface; see the [CLI reference](cli.md) for command details.

## Audit logs

`audit.log` is the authoritative, append-only JSON Lines audit record. Each entry has a raw 26-character ULID, actor/source/result fields, and a SHA-256 predecessor hash; each append is synced before the event is mirrored to the queryable `audit_log` table. The mirror receives the same recursively sanitized details as the file. A failed mirror emits an `audit.mirror_failed` audit event and does not remove or suppress the file entry. Rotations use the UTC date and a numeric suffix when a log rotates more than once per day; `audit.anchor` preserves the chain head across retention. The logs contain full normalized client addresses for network events; Tor requests use the exported circuit identity or the literal `tor` sentinel instead of loopback. The audit log is read from the server filesystem, not a web page.

Backups can contain server configuration, secrets, database contents, and optional application data. With a remote database, the provider manages remote contents and the archive includes the local read-cache snapshot only when caching is enabled. Store the backup directory with restricted permissions and configure `server.backup.encryption_password` in `secrets.yml` to encrypt archives. The password is operator-managed and is not generated. Enabling any `server.compliance` standard blocks backup creation until encryption is configured. Restore is available only through the local CLI; it prompts for encrypted archive passwords without echoing them. Restoring over a populated database requires typed confirmation when running as root, or the operator token when running as the service account. Other users cannot overwrite a populated database. Restore enforces archive expansion limits and validates the SQLite database before installation. Retain old encryption passwords for archives created before a password change; rotation does not re-encrypt existing files.

Responses include content-type, framing, referrer, content-security, cross-origin, permissions, request ID, and permitted cross-domain policy headers. HSTS is returned only for direct TLS requests. Same-origin state-changing browser forms require a CSRF token.

## TLS certificates

When TLS is enabled, the server selects certificates from the configured certificate files, the system Let's Encrypt directories, the app-managed `{config_dir}/ssl/letsencrypt/{fqdn}/` directory, then `{config_dir}/ssl/local/{fqdn}/`. Certificates must be readable, unexpired, and match the configured host. Only app-managed Let's Encrypt certificates renew automatically when 30 days or fewer remain; system and local certificates remain operator-managed. HTTP-01 and TLS-ALPN-01 use the server's existing HTTP and HTTPS listeners. DNS-01 supports every lego DNS provider; its flat provider credential map is encrypted into `secrets.yml` with the server encryption key and is never logged or returned. See [configuration](configuration.md#tls-and-lets-encrypt) for challenge, listener, certificate-selection, and credential setup details.

## Vulnerability reporting

Report project-source vulnerabilities privately through [GitHub Security Advisories](https://github.com/apimgr/zipcodes/security/advisories/new). A deployed instance can also accept reports through `/server/security` and the `/server/contact?security_id=...` form. Security reports use the project OpenPGP key at rest when one exists, and AES-256-GCM otherwise; SMTP delivery attaches the encrypted report. Configured security webhooks receive only an event summary with the tracking ID and the CLI command operators use to retrieve the encrypted report. An acknowledgment contains the tracking ID and a status URL. When a researcher submits an armored OpenPGP public key or an HTTPS key URL, the email acknowledgment is encrypted to that key. Without working SMTP, the report is still stored and webhook summaries remain available, while email acknowledgments are disabled. The status URL exposes triage state only, not report content. Operators can use `zipcodes --maintenance security list`, `show`, `export`, and `update` to manage report metadata and obtain the encrypted report body; the commands never print report contents. A status change sends a status-only notice when SMTP works, encrypted to the researcher's key when available.

The security form's optional CVE request is stored in the encrypted report and as metadata. Maintainers initiate CVE assignment after triage when requested.

`/.well-known/security.txt` includes the GitHub advisory URL, a rotating instance-report URL when contact reporting is enabled, a configured security contact when available, an `Encryption:` URL when the project PGP key is enabled, an annual expiration time, `Preferred-Languages: en`, and request-derived policy and `Canonical` URLs. `/.well-known/pgp-key.asc` serves the armored public key only while a keypair exists and `web.security.publish_pgp_key` is enabled. Generate, rotate, export, import, publish, and delete keys with `zipcodes --maintenance pgp`; private key files are encrypted with the database `installation_secret` and stored under `{config_dir}/security/`. Rotation re-encrypts retained PGP reports in one database transaction, retains the previous private key for 30 days for in-flight messages, and is recovered at startup if interrupted. A second rotation during that period replaces the earlier retired key with the key being rotated, restarting the 30-day retention period. Keyserver submissions are tracked in `keyservers.state` and retried by the scheduler.

Backups include `security/pgp.pub.asc`, `security/pgp.priv.asc.enc`, and `security/keyservers.state` alongside the database report records. They also include `app_secrets.json`, the complete `app_secrets` snapshot containing `installation_secret` and previous-key rows, including when the database is remote and has no local cache. Restore replaces the stored application secrets with that snapshot. `zipcodes --maintenance backup test` verifies the private/public key fingerprint using the bundled installation secret without changing live files; this also works for remote-database backups without `server.db`.

## Public and discovery endpoints

- `/server/healthz` is public; its root `/healthz` alias is disabled by default and can be enabled with `server.healthz.root.enabled`. `/api/{api_version}/server/healthz` and `/api/healthz` are machine endpoints. See [API reference](api.md) for content negotiation.
- `/.well-known/llms.txt` and `/llms.txt` list the public API and documentation routes without private configuration.
- `/.well-known/security.txt` is the canonical security contact file.
- `robots.txt` and `sitemap.xml` expose public crawling guidance and public HTML routes.
- Unknown `/.well-known/*` paths return `404`. No WebFinger, OAuth/OIDC metadata, app association, or MTA-STS endpoint is enabled.
